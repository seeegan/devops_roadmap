Есть фундаментальная и довольно простая идея - "**В Linux (и UNIX вообще) всё есть файл**". Будь это программа, драйвер или обычный текстовый документ, это всё "файл".

Файл - с точки зрения Linux это сущность имеющая разные части которые друг от друга хранятся отдельно.

- Содержимое файла - хранится на самом диске, в виде данных записанных на блочном устройстве. У этих данных есть свой "адрес" по которому ядро (процесс) может с ним взаимодейсвовать. Этот адрес хранится в `inode`.
- `inode` - (index node - индексный узел) метаданные файла, в которых содержится (размер файла, его владелец, права на файл, дата создания, счётчик жёстких ссылок `hard links`). Грубо говоря это "паспорт" нашего файла
- Имя файла и номер индексного узла (`inode`). Эти данные хранятся как записи в `Directory entry`. `Directory Entry` - это запись в каталоге файловой системы, которая хранит имя файла и номер его `inode`.

> Важно! Имя файла - это не часть файла, это запись в каталоге, которая указывает на файл (указателем на файл является `inode`). То есть имя файла - не является его частью, по причине того, что у этого файла может быть несколько имён (жёстких ссылок) или не иметь вообще имени (если файл открыт процессом, но был удалён)

### Пример

Допустим мы создадим файл `test_file` и добавим в него запись `Hello World!`

```shell
touch /home/user/test/test_file
```

```shell
echo "Hello World!" > /home/user/test/test_file
```

Посмотрим что у нас получилось
```shell
ls -li /home/user/test
```
![](../pages/attachments/Pasted%20image%2020261117071635.png)
- `-l` - флаг для подробного вывода
- `-i` - флаг для отображения `inode number`

`259919` - это номер `inode`, идентификатор индексного узла в котором есть адрес на содержимое файла

А теперь давайте создадим жёсткую ссылку на `test_file` и назовём её `hard_link_to_file`
```shell
ln test_file hard_link_to_file
```


И снова посмотрим что у нас получилось:
```shell
ls -li
```
![](../pages/attachments/Pasted%20image%2020261117072054.png)
Номер индексного узла (`inode`) не изменился, он точно такой же, а также счётчик ссылок что я выделил красным цветом на скриншоте стал больше = `2`.

Данный пример отображает, что имя файла - это просто запись в каталоге, она ничего не значит, сама информация о файле хранится в `inode`.

Мы разобрались что такое `inode`, это паспорт файла, но как узнать где живёт этот файл? Где в этом паспорте найти его прописку?

Чтобы узнать на каких физических номерах блоков хранится содержимое файла, мы можем использовать программу `filefrag`
```shell
filefrag -v /home/user/test/test_file
```
- `filefrag` - file + frag (сокращение от fragmentation - флагментация). Программа для отчёта о фрагментации файла.
- `-v / --verbose` - подробный вывод

![](../pages/attachments/Pasted%20image%2020261117073900.png)

Что мы видем в выводе программы?

- наш файл весит 13 байт и занимает один блок на диске
- номер блока на диске который занимает наш файл - `597030`
- 1 `extent` - означает что файл не фрагментирован, значит он целый, не разбит на маленькие части.

`filefrag` мы использовали для того, чтобы понять что `inode` != номер блока на диске. `inode` - это паспорт файла, который в том числе содержит и адрес (номер блока на диске) где живёт наш файл.

## Процесс создания файла в Linux с полного нуля.

### Шаг 1: Создаём "сырой" диск (Loopback-устройство)
Нам нужен диск, мы можем либо его приобрести, вставить в нашу виртуальную машину и он бы отображался у нас в "псевдо-файловой системе" `/dev`. Например это был бы `/dev/sda`. Но так как физического диска у нас нет, то мы можем просто создать файл, который ядро будет воспринимать как полноценный диск. Для этого мы будем использовать `dd`.

```shell
dd if=/dev/zero of=/tmp/my_disk.img bs=1M count=100
```
- `dd` - data duplicator - утилита для копирования данных
- `if= / --input-file` - входящий файл(откуда берём данные).
- `of= / --output-file` - исходящий файл (куда записываем данные). `/tmp/my_disk.img` - наш будущий "диск".
- `bs= / --block-size` - размер блока (1 мегабайт)
- `count=` - количество блоков (100 блоков по 1МБ = 100МБ)
![](../pages/attachments/Pasted%20image%2020261118003304.png)

Проверяем что наш "диск" действительно был создан
```shell
ls -lh /tmp
```
![](../pages/attachments/Pasted%20image%2020261118003351.png)
Наш будущий "диск" создан, весит 100МБ

Можем посмотреть что внутри этого диска с помощью программы `xxd`.
```shell
xxd /tmp/my_disk.img | head -10
```
- `xxd` -  `xx` - Это  две шестнадцатеричные цифры (от англ. hex или hexadecimal - шестнадцатеричный). А `d` это сокращение от `dump` (сброс/дамп). `dump` - это резервная копия или снимок состояния, то есть ядро делает копию состояния нашего диска и предоставляет нам информацию в виде `output`
![](../pages/attachments/Pasted%20image%2020261118003541.png)
Пока тут только нули, это нормально так как мы на сам диск ещё ничего не записывали кроме нулей.

До момента пока мы не создали и не смонтировали наш диск - он не является блочным устройством, это просто обычный файл
```
-> #Прочерк означает что это обычный файл, у блочного устройства в начале идёт b.
-rw-r--r--  1 root root 104857600 Nov 17 20:32 my_disk.img
```

```shell
file /tmp/my_disk.img
/tmp/my_disk.img: data
```

### Шаг 2: Создаём файловую систему (`mkfs`)

Сейчас наш файл `/tmp/my_disk.img` - это просто набор нулей. Ядро не знает как с ним взаимодействовать. Нам нужно "форматировать" его, то есть создать на нём структуру, которая называется "файловая система" (`File System`)

Для этого используется программа `mkfs`(make file system - создать файловую систему)

```shell
sudo mkfs.ext4 /tmp/my_disk.img
```
- `sudo` - superuser do - выполнить от имени суперпользователя (root)
- `mkfs.ext4` - make file system ext4 - создать файловую систему типа `ext4` (стандартная для Linux)
- `/tmp/my_disk.img` - наш "диск".

#### Что произойдёт
`mkfs.ext4` возьмёт наш файл-диск и запишет в него суперблок (superblock), таблицу `inode` и блоки данных (data blocks). Он создаст ту самую структуру, которую мы разбирали ранее.
![](../pages/attachments/Pasted%20image%2020261118005544.png)
Количество `inode` мы не указывали, он взял значение по умолчанию.

Теперь можем снова посмотреть содержимое диска и найти его суперблок, который обозначает что это файловая система типа - `ext4`
```shell
xdd /tmp/my_disk.img | grep "00000400"
```
![](../pages/attachments/Pasted%20image%2020261118010304.png)
Вот и наш суперблок.

Изменился и тип файла нашего "диска"
```shell
file /tmp/my_disk.img
```
![](../pages/attachments/Pasted%20image%2020261118010408.png)
Теперь это файловая система, имеющая свой `UUID`, а не просто файл с данными.
Система всё ещё не видит наш диск, несмотря на то, что мы уже записали на него файловую систему.
```shell
df
```
![](../pages/attachments/Pasted%20image%2020261118010619.png)
Тут нет нашего диска, а всё потому что мы ещё не монтировали его.

### Шаг 3: Монтирование
Процесс монтирования выглядит с одной стороны простым, но как только попросят рассказать про процесс монтирования, тут и начитаются трудности. Нам нужно понять что за такая концепция "монтирования" и зачем она нужна.

Монтирование (`mount`) - это процесс, при котором ядро Linux делает файловую систему (которая лежит на каком-то устройстве) "**доступной**" через дерево директорий.

> Поясню, сейчас наш новоиспечённый диск (`/tmp/my_disk.img`) на который мы записали файловую систему - недоступен, это просто диск с файловой системой.

Чтобы он стал доступен, нам нужно его монтировать в какую-то директорию.

#### Проблема которую решает монтирование
В `Linux` нет понятия "диск C:" или "диск D:". Есть только одно "**дерево директорий**", которое начинается с корня `/`.
Когда ты вставляешь флешку или подключаешь диск, система не знает, куда его "положить".
Монтирование - это способ встроить новый диск в это дерево.

Аналогия:
Представь, что у тебя есть шкаф (корневая файловая система `/`). В шкафу есть полки (директории). Ты принёс новую коробку (диск с файловой системой `/tmp/my_disk.img`). Чтобы иметь к ней доступ, ты ставишь эту коробку на одну из полок (директорию) этого шкафа. Эта полка и есть точка монтирования (mount point). Всё, что было в коробке, теперь доступно через эту полку.

Технически:
В ядре есть структура `VFS`(Virtual File System) - виртуальная файловая система. Она абстрагирует работу с разными типами файловых систем (`ext4`,`xfs`,`nfs`). Когда ты монтируешь устройство в точку, `VFS` связывает `inode` директории-точки монтирования с корневым `inode` новой файловой системы.

Как это работает (по шагам)
1. Ядро проверяет устройство. Оно читает суперблок (superblock) с диска, чтобы понять какой тип файловой системы (`ext4`,`xfs`,`vfat`) и в каком она состоянии.
2. Ядро проверяет точку монтирования. Директория (например `/mnt/testfs`) должна существовать и быть пустой (или почти пустой). Если там были файлы, они станут "скрытыми" (мы ранее об этом говорили)
3. Ядро создаёт связь. Оно создаёт запись в таблице монтирования (mount table) и связывает `inode` директории с корневым `inode` файловой системы.
4. Доступ. Теперь, когда ты заходишь в `/mnt/tesfs`, ядро перенаправляет тебя не в пустую директорию на корневой ФС, а в корень новой ФС на диске.

#### Практика (монтируем наш диск)

1. Сначала нужно создать точку монтирования (директорию). Как это делать мы уже знаем:
	```shell
	mkdir /mnt/testfs
	```

2. Монтируем:
	```shell
	sudo mount -o loop /tmp/my_disk.img /mnt/testfs
	```
	- `mount` - смонтировать, программа для монтирования файловой системы в директорию
	- `-o / --options` - опции. Передаём опцию `loop`
	- `loop` - loopback - петлевое устройство (использовать файл как блочное устройство)
	- `/tmp/my_disk.img` - устройство (device), которое мы монтируем
	- `/mnt/testfs` - точка монтирования (mount point), куда монтируем
	
3. Проверяем:
	```shell
	df -h /mnt/testfs
	```
	![](../pages/attachments/Pasted%20image%2020261118015431.png)
```shell
findmnt /mnt/testfs
```
![](../pages/attachments/Pasted%20image%2020261118015526.png)

4. Смотрим на таблицу монтирования
   ```shell
   mnt | grep "/mnt/testfs"
   ```
![](../pages/attachments/Pasted%20image%2020261118015644.png)

Всё получилось! Можем ещё посмотреть на список блочных устройств, `/dev/loop0` должен там появится и его точка монтирования должна быть `/mnt/tesfs`
```shell
lsblk
```
![](../pages/attachments/Pasted%20image%2020261118015755.png)

В привычной среде, мы бы просто подключили диск, он бы распознался как блочное устройство и мы могли бы сразу его смонтировать, но в нашем примере мы не только смонтировали, но создали файл, записали на него файловую систему и смонтировали его через драйвер `loop` тем самым он стал блочным устройством.

Ещё очень важная информация. При `mount` в точку монтирования, те файлы что были в точке монтирования не удаляются, но они становятся скрытыми.
Давай в этом убедимся на конкретном примере, у нас уже есть диск `my_disk.img`, у нас есть точка монтирования `/mnt/user_fs`, давай перед тем как туда смонтировать наш диск что-то туда поместим.

```shell
sudo touch /mnt/user_fs/test_file.txt
ls -la /mnt/user_fs/
```
![](../pages/attachments/Pasted%20image%2020261119052300.png)
Вот наш файл, теперь мы монтируем наш диск в эту директорию где уже что-то лежит.

```shell
sudo mount -o loop /home/user/my_disk.img /mnt/user_fs/
ls -la /mnt/user_fs
```
![](../pages/attachments/Pasted%20image%2020261119052450.png)
Нашего файла `test_file.txt` не видно, его нет.

А теперь размонтируем диск (отключим его) из точки монтирования и снова посмотрим на нашу директорию

```shell
sudo umount /mnt/user_fs
ls -la /mnt/user_fs
```
![](../pages/attachments/Pasted%20image%2020261119052620.png)
Из чего следует, что не стоит монтировать диск в точку монтирования на которой уже что-то есть, мы просто не будем видеть этих файлов.

А что произойдёт с `inode` этого файла? Сможем ли мы его найти по номеру? Давайте попробуем.

Сначала убедимся что файл есть:
```shell
sudo find / -inum 129644 2>/dev/null
```
![](../pages/attachments/Pasted%20image%2020261119052950.png)

Теперь снова монтируем наш диск:
```shell
sudo mount -o loop /home/my_disk.img /mnt/user_fs
ls -la /mnt/user_fs
```
![](../pages/attachments/Pasted%20image%2020261119053348.png)

Попробуем найти наш файл по номеру `inode`:
```shell
find / -inum 129644 2>/dev/null
sudo find / -inum 129644 2>/dev/null
```
![](../pages/attachments/Pasted%20image%2020261119053457.png)
Ничего нет, как мы уже ранее обсуждали, номер `inode` ровно как и имя файла хранится в `Directory Entry`, монтированием мы перезаписали директорию, соответственно и номер `inode` с именем файла просто не отображается, но он всё ещё существует в системе. Если бы мы записали какую-то информацию в наш текстовый файл, то он бы и занимал место на блоках диска, несмотря на то, что он не виден в системе.
