### `df`

`df`, расшифровывается как `disk free` то есть дословно сколько свободного места на диске осталось, но это не весь её функционал, она довольно информативная если использовать разные флаги для её вызова.
```shell

```

###  `du`

`du`, расшифровывается как disk usage - дословно "**Сколько места занимает директория или файл**"
Если с помощью утилиты `df` мы определили какая файловая система забита, то с помощью `du` мы сможем определить какая именно директория или файл является "**виновником**".
Давайте продемонстрируем как это работает, с помощью утилиты `fallocate` мы создадим файл который исскуственно займёт 1Gb места на диске.
```shell
fallocate -l 1G /home/seegan/testfile
```
`fallocate` - ключевое слово для взаимодействия с утилитой
`-l` - флаг позволяет указать желаемый размер файла
`path` - ну и указываем имя или путь+имя файла который мы хотим создать

Помните, мы говорили что с помощью `df directory` можно узнать к какой ФС принадлежит каталог или файл?
```shell
df /home/seegan/testfile
```
![](../attachments/Pasted%20image%2020261012164839.png)

Допустим что мы не знаем что файл `/home/seegan/testfile` занимает 1Gb места, мы просто ввели `df -h` и увидели что почему-то наша файловая система стала на 1Gb меньше свободного места.

Чтобы определить кто "**виновник**" воспользуемся утилитой `du`
```shell
du -ah /home/seegan 2>/dev/null | sort
```
![](../attachments/Pasted%20image%2020261012233655.png)
>Вот и нашёлся "**виновник**".

Таким образом с помощью `df` - мы определили какая ФС "хорошо покушала", а с помощью `du` - определил что именно она сьела)

Ещё поиском таких файлов можно пользоваться утилитой `find`, я бы даже сказал что она больше для этого подходит, она очень гибкая и можно не только указывать размер, имя и остальные параметры для поиска нужного нам файла под шаблон что мы указали.
##### Пример
Как узнать какой файл/файлы в системе  занимают больше 1Gb места?
```shell
find /home -size +900
```
`find` - ключевое слово для взаимодействия с утилитой
`/home` - указываем путь по которому мы будем искать, можно указать и корень `/`
`-size` - флаг для указания размера в пределах которого мы будем искать
	`+n` Точно **больше** того числа что мы указали
	`-n` Точно **меньше** того числа что мы указали
	`n`  Ровно столько сколько мы указали

> Эта инфа немного вне темы, но этот инструмент очень мощный, не упомянуть его было бы ошибкой.


##### Ключевые флаги
`-max-depth=N` - говорит: "показывай только N уровней в глубь"
	Если мы хотим посмотреть сколько занимает корень в файловой системе, то без указания этого флага мы получим тысячи строк, а нам это не нужно
```shell
sudo du -h / --max-depth=0 2>/dev/null
```
`2>/dev/null` - 2 это файловый дескриптор `STDERR`, чтобы просто посмотреть сколько занимает директория мы весь поток ошибок направляем на устройство `/dev/null`
![](../attachments/Pasted%20image%2020261012233135.png)

`-a` - показывает не только каталоги, но и все файлы в каталоге, таким образом можем 100% что занимает больше всего места в каталоге
	![](../attachments/Pasted%20image%2020261012233421.png)


### `lsof`

`lsof` расшифровывается как list open files - список открытых файлов

Как нам уже известно "**В Linux всё файл**", а значит любой используемый драйвер, log-файл или конфигурационный файл можно посмотреть через lsof. То есть какая программа открыла этот файл и использует его прямо сейчас.

Когда какая-то программа что-то открывает - она получает `fd` - `file descriptor`. `lsof` показывает все открытые файлы в системе и процессы которые их открыли.

А теперь немного углубимся что такое `fd` - `file descriptor`. Ибо без понимания этой темы дальше будет тяжело понимать без абстракций что происходит при открытии файла какой-либо программой.

##### `fd` - `file descriptor`

Что такое `file descriptor`?
>`File descriptor (fd)` - это целое неотрицательное число, через которое процесс обращается к открытому файлу (или сокету, устройству, пайпу)

Если уж прям упростить, то `fd` - это "**номерок**", который ядро выдаёт процессу, когда тот что-то открывает.

---
###### Аналогия из жизни

Ты сдаёшь куртку в гардероб:
-  Ты cдаёшь куртку
-  Гардеробщик вешает её на крючок №42
-  Даёт тебе жетон с номером 42
-  Когда ты хочешь забрать твою куртку, то гардеробщик конечно же не помнит какой у тебя был номер, ведь он каждый день видит много людей. Для этого ты ему отдаёшь **свой номер**

В Linux всё почти также:
-  Куртка = файл на диске
-  Крючок = место в памяти, где ядро хранит информацию о файле
-  Жетон с номером 42 = `file descriptor`

> Процесс не работает с файлом напрямую. Он говорит ядру: "прочитай мне из `fd = 42` ". Ядро по этому номеру находит, какой файл имеется в виду.

###### Что происходит в системе при открытии файла

Для открытия файла используется системный вызов к ядру `open("file_path")`:
- Ядро находит `inode` файла на диске
- Создаёт `open file descriptor` - структуру в памяти с флагами (`read`/`write`), позицией чтения
- Находит свободный `fd` в таблице процесса (обычно следующий по порядку)
- Связывает `fd=3 -> open file descriptor -> inode`
- Возвращает число 3 процессу
- Дальше процесс делает `read(3, buffer, size)` - и ядро знает, откуда читать


##### Стандартные `fd`

Может быть вы уже слышали про стандартные потоки `STDIN - 0`, `STDOUT - 1`, `STDERR - 2`
Так вот, это тоже файловые дескрипторы, точнее не "тоже", а это стандартные файловые дескрипторы.


| `fd` | Имя      | Что значит                          |
| ---- | -------- | ----------------------------------- |
| `0`  | `stdin`  | Стандартный ввод (клавиатура)       |
| `1`  | `stdout` | Стандартный вывод (терминал)        |
| `2`  | `stderr` | Стандартный вывод ошибок (терминал) |

Отсюда та самая классика перенаправления вывода, или ошибок в отдельный файл
```shell
command > file.txt       # stdout (fd=1) -> файл
command 2> error.txt     # stderr (fd=2) -> файл
command > out.txt 2>&1   # stdout и stderr -> в один файл
command < input.txt      #stdin (fd=0) <- файл 
```

Что делает 2>&1:
- `2>` - **перенаправить fd=2 (stderr)**
- `&1` - **"в то же место, куда ведёт fd=1".**
- Результат: `stderr` и `stdout` идут в один файл

Порядок важен!
```shell
command 2>&1 > out.txt   # НЕПРАВИЛЬНО — stderr идёт в терминал, stdout в файл
command > out.txt 2>&1   # ПРАВИЛЬНО — оба идут в файл
```
>Потому что `2>&1` копирует **текущее** состояние fd=1. Если `> out.txt` ещё не выполнен — fd=1 ведёт в терминал.

**Всё нужно закреплять на практике, иначе всё будет абстрактно**

##### Что такое `lsof`

Определение мы уже записали, в Linux - всё есть файл, от этого и пляшем. Когда процесс что-то открывает - он получает свой `fd` (`exec n > /somefile`). `lsof` показывает все `fd` во всех процессах системы

Если более проще: `lsof` - это как `ls` для таблицы `fd` всех процессов сразу.

##### Откуда `lsof` берёт данные

Мы помним, что `fd` процесса можно посмотреть так:
```shell
ls -l /proc/$PID/fd
```

`lsof` делает тоже самое, но:
- Проходит по всем процессам сразу
- Читает `/proc/$PID/fd/*`
- Читает `/proc/$PID/maps`  (для memory-mapped файлов) - наверное это разберём потом
- Читает `/proc/net/*` - (для сетевых сокетов) - тоже пройдём потом
- Форматирует всё в одну таблицу

`lsof` - это удобная обёртка над `/proc`.

Давай разберём на примере `nginx`
- Сначала определим какой у него PID
	```shell
	ps aux | grep "nginx"
	```
	![](../attachments/Pasted%20image%2020261012215049.png)
	> Нас интересует именно `nginx: master process`
	
	Зная его `PID` мы можем посмотреть какие файловые дескрипторы у него есть
	```shell
	ls -l /proc/2913/fd
	```
	![](../attachments/Pasted%20image%2020261012215257.png)
	>Сначала пользуемся не совсем удобными для нас способами, чтобы понимать что делает `lsof`
	
	Определи, какие файловые десрипторы у него есть, и в какие файлы они пишут, обратите внимание, `/var/log/nginx/error.log` - это лог для ошибок, в него пишется ошибки возникшие в процессе `nginx` которые сначала попадают в `STDERR - fd2` и потом перенаправляются в `/var/log/nginx/error.log`. А в `fd3` - это уже новый файловый дескриптор записываются события связанные с доступом, авторизацией в `nginx`.

		- `/proc/$PID/maps`  (для memory-mapped файлов) - наверное это разберём потом
		- `/proc/net/*` - (для сетевых сокетов) - тоже пройдём потом
		- Формирует всё в одну таблицу

	Если пользоваться `lsof` без аргументов, то мы получим огромную портянку, невозможно будет что-то читать, поэтому сначала стараемся определить `PID` и потом идём в `lsof`.

##### Ключевые флаги `lsof`

`lsof` позволяет нам искать не только по `PID` , но и по самому файлу. Указав путь до файла у которого мы хотим узнать какой процесс его использует мы увидим это.
```shell
lsof /var/log/nginx/access.log
```
![](../attachments/Pasted%20image%2020261012220748.png)
`PID` - номер процесса который использует этот файл
`USER` - пользователь (владелец) файла
`NAME` - путь до файла
`NODE` - номер `inode` файла
	Offtop- утилитой `find` можно найти файл по его `inode` - `sudo find / -inum $inode_number`

Для чего вообще использовать `lsof`?
Представь что у тебя на сервере закончилось место на диске, что ты будешь делать?
- Сначала я зайду в терминал и введу `df -h`, посмотрю какие файловые системы забиты
- После того как я определил какая файловая система забита в "край", через `du -h` смогу определить в каком каталоге лежит этот файл который занимает много места
- Через `find /$DIR -size +n` смогу определить какой именно файл занимает много места
- Попытаюсь его удалить `rm $file`. Но вот тут появляется ошибка... Файл `busy` - что означает он "занят" каким-то процессом. Как в Windows, если какая-то программа использует файл, то ты его не сможешь закрыть пока не закроешь сам процесс, вот в Linux также.
- Теперь нужно понять каким образом можно определить какой процесс использует этот файл
- Как раз таки с помощью `lsof /path_to_file/file` ты сможешь определить какой процесс или процессы его "держат"
- Через `systemctl stop` - если этот процесс заведён как сервис остановишь процесс (или через `kill $PID`) и после этого сможешь уже удалить сам файл.

##### А теперь самое вкусное и интересное

Сразу приступим к практике.
Зафиксируем наше текущее состояние диска, насколько он заполнен
```shell
df -h /
```
![](../attachments/Pasted%20image%2020261012223344.png)

Теперь создадим файл размером 1Gb и заполним его блоками

dd if=/dev/zero of=/home/seegan/testfile bs=1M count=1024

![](../attachments/Pasted%20image%2020261012224508.png)

Если мы сейчас просто удалим файл, то будет скучно, да, диск освободится на 1Gb и всё.

Теперь этот файл нужно "занять" процессом, для этого мы создадим уже знакомый нам `fd`
```shell
exec 3>> /home/seegan/testfile
```
![](../attachments/Pasted%20image%2020261012223739.png)
Файловый дескриптор создался и "захватил" наш файл. 

А теперь давай попробуем удалить наш файл и посмотреть освободилось ли место на диске?
```shell
rm /home/seegan/testfile
df -h /
```
![](../attachments/Pasted%20image%2020261012224850.png)
> 	Как видим, место не освободилось, а значит что наш файл сейчас держит процесс `shell`

![](../attachments/Pasted%20image%2020261012224953.png)

Допустим мы зашли на сервер и удалили, файл, но ничего не изменилось, что делать дальше?
```shell
lsof /home/seegan/testfile
```
![](../attachments/Pasted%20image%2020261012225125.png)

Ситуация патовая, мы удалили файл, место не освободилось, но и сам файл "пропал", что делать????

Для этого есть флаг `+L1`
```
lsof +L1
```
`+L1` - "файлы с link count < 1". То есть файлы, удалённые с диска, но всё ещё открытые процессом
Файл фактически не отображается в системе, но у него осталась inode и до тех пор пока она есть он не может быть удалён безвозвратно.
![](../attachments/Pasted%20image%2020261012225712.png)

Давай мы пока его удалять не будем, научимся сначала восстанавливать.
Какой путь мы прошли?
- Посмотрели через `df -h /` сколько места на диске свободно
- Создали файл и наполнили его нулями `dd if=/dev/zero of=/home/seegan/testfile bs=1M count=1024` 
- Создали новый файловый дескриптор и привязали его к нашему файлу `exec 3>> /home/seegan/testfile`
- Удалили файл `rm /home/seegan/testifle` , но место не освободилось
- Теперь восстановим файл, мы уже знаем что на данный момент процесс shell с  `fd3` "держит наш файл", чтобы его восстановить нам нужно скопировать содержимое нашего процессора и нужного нам файлового дескриптора в отдельную папку
	```shell
	cp /proc/$$/fd/3 /home/seegan/testfile
	```
	![](../attachments/Pasted%20image%2020261012230501.png)
	И вот пожалуйста, наш файл восстановлён, только есть один нюанс, это уже новая `inode` так как жёсткой ссылки не было на файл и мы просто скопировали содержимое файлового дескриптора в изначальную папку.

Старый файл всё ещё зарезервирован
![](../attachments/Pasted%20image%2020261012230730.png)

А места на диске стало ещё меньше, потому что:
- Старый файл всё ещё "держится" процессом с файловым дескриптором `fd3`
- И мы ещё восстановили тот файл под новой `inode` 
- По итогу два файла по 1Gb

А теперь давай всё почистим
- Восстановленный файл никем не держится, это можно проверить через `lsof`
![](../attachments/Pasted%20image%2020261012231017.png)
- Значит мы можем его удалить
- А чтобы окончательно отпустить наш изначальный файл, то есть несколько способов:
	 1. Убить процесс который "держит этот файл" - `kill $PID`
	 2. Перезаписать этот файл - `> /proc/$$/fd/3`, после перезаписи место освободится
	 3. Направить файловому дескриптору операцию завершения - `exec 3>&-`
	```shell
	exec 3>&-
	```
	![](../attachments/Pasted%20image%2020261012231352.png)
	Всё, файловый дескриптор остановлен и файл был отпущен в преисподню)

Ну и конечно же место на нашем диске освободилось
![](../attachments/Pasted%20image%2020261012231500.png)



### Вывод
Мы познакомились с утилитами:
`df` - disk free, отображает не только свободное место на диске, но и показывает сколько `inodes` есть, используется и сколько свободно
`du` - disk usage, отображает сколько занимает места на диске каталог или файл
`df` - файловый дескриптор, это целое неотрицательное число через которое процесс взаимодействует с файлом, получает он информацию о файле через `inodes` - в которой есть адрес на диске на котором располагается содержимое файла
`lsof` - list open files, очень сильная утилита, можно смотреть не только какие файлы используются тем или иным процессом, но ещё и смотреть какие порты заняты и кем заняты.
`find` - немного поговорили про `find` интересная утилита для поиска файлов по шаблону
