# No route to host

У меня не получается скачать busybox по ссылке (https://busybox.net/downloads/busybox-1.38.0.tar.bz2) через свою VM. Разобьём проблему на маленькие шажки, посмотрим на каком из уровней OSI возникла ошибка и как её решить.

```shell
wget https://busybox.net/downloads/busybox-1.38.0.tar.bz2
```
![](../attachments/Pasted%20image%2020261120011059.png)
Мы видим строку `Resolving busybox.net (busybox)... 140.211.167.122`, это нам говорит о том что `DNS` протокол работает в штатном режиме, он наше доменное имя `busybox.net` смог превратить в `ip-адрес`.

```shell
nslookup busybox.net
```
![](../attachments/Pasted%20image%2020261120011301.png)

`192.168.11.116` - это `ip-адрес` моего `DNS - сервера`, а значит мой хост сначала идёт на `192.168.11.116` и от него получает `ip-адрес по доменному имени`.

Убедится что он обращается к `DNS-серверу` можно посмотрев `/etc/resolv.conf`
```shell
cat /etc/resolv.conf
```
![](../attachments/Pasted%20image%2020261120011520.png)

### Шаг 1: Проверка маршрутизации (`route`)
Как мы уже ранее изучали, перед тем как отправить куда-то пакет (запрос) он попадает на нашу сетевую карту, и если правила `firewall` не запрещают то он уходит в сеть. Но пакет должен идти по какому-то пути, такие пути и называются `route`, нам нужно проверить есть ли у нас вообще путь по которому пакет может обратиться в глобальную сеть.

```shell
ip route
```
![](../attachments/Pasted%20image%2020261120013216.png)
У нас есть два `route`:
- `default` - это и есть наш выход в сеть, все `ip-адресса` не подходящие под маску `192.168.11.x` идут через него, остальные подходящие гуляют внутри одной сети `192.168.11.x`, такие пакеты доходят сразу так как они в одной сети.
- `192.168.11.0/24` - это наш `localhost` с маской `/24`, означающей что в одной сети может находиться `254` адреса, `192.168.11.1` - это `ip-адрес` самой сети - `GATEWAY`, а `192.168.11.255` - это широковещательный адрес, пакеты которые мы отправляет на него доходят до всех устройств в сети.

Значит мы определили, путь для выхода в сеть у нас есть, но почему-то мы получаем ошибку `no route to host`, дословно - узел недоступен. Давайте разбираться что не так.

Маршрут по умолчанию у нас есть, значит сеть у нас настроена неверно.

Стоит проверить, видит ли ядро наши сетевые интерфейсы
```shell
ip addr
```
![](../attachments/Pasted%20image%2020261120014021.png)
Сетевые интерфейсы есть, ядро их видит.

Идём дальше, если сетевой интерфейс есть и ядро его видит, значит ядро блокирует исходящие соединения, то есть `firewall`, нужно посмотреть какие правила в `iptables` у нас вообще есть. Возможно там кроется тайна.

```shell
sudo iptables -L -n -v
```
![](../attachments/Pasted%20image%2020261120014414.png)

Никаких правил запрещающих выход пакета в сеть не видно, значит дело не в `firewall`.


Посмотрим на таблицу протокола `ARP`. Мы уже слышали про это протокол, для этого нужно выполнить команду `ip neigh`

```shell
ip neigh
```
![](../attachments/Pasted%20image%2020261120230822.png)
Видим странный статус напротив `ip-адреса` нашего `default route`. Помните мы смотрели какие у нас есть роуты и какой стоит по умолчанию для выхода в глобальную сеть?
![](../attachments/Pasted%20image%2020261120013216.png)

Правильно, `192.168.11.1` - это адрес через который наша машина обращается в глобальную сеть и не может установить `TCP` соединение. Уже догадываетесь? Да, всё верно, те самые врата `(GATEWAY)` через которые мы пытаемся достучаться до `busybox.net` на самом деле недоступны. Давайте в этом убедимся:
```shell
ping -c 3 192.168.11.1
```
![](../attachments/Pasted%20image%2020261120231212.png)
`Destination Host Unreachable` - ошибка обозначающая что "адрес назначения (`192.168.11.1`)" - недоступен. Но как так вышло? На самом деле очень просто, я вручную настраивал выдачу `ip-адресов` машинам, `DHCP` я отключил, а значит не зная адреса `GATEWAY` я указал значение по умолчанию `192.168.11.1`. Это можно посмотреть в `netplan`:
```shell
sudo cat /etc/netplan/*.yaml
```
![](../attachments/Pasted%20image%2020261120231513.png)

Хорошо, раз мы определили что default route у нас неверный, на самом деле на данном адресе вообще ничего не располагается, этот адрес никем не занят. Какой тогда адрес у `GATEWAY` фактически? Это можно выяснить методом исключения или посмотреть опять же на таблицу `ARP` и сравнить `MAC-адреса`.

```shell
ip neigh
```
![](../attachments/Pasted%20image%2020261120232128.png)
Посмотрим на наш `router`, его `ip` адрес записан в формате `ipv6`, но `MAC-адрес` остаётся неизменным, давайте посмотрим у каких ещё `ipv4` адресов такой же адрес.
```shell
ip neigh | gpep "78:4f:24:86:eb:96"
```
![](../attachments/Pasted%20image%2020261120232310.png)
А вот и он, давайте попробуем его пингануть.
```shell
ping 192.168.11.254
ip neigh
```
![](../attachments/Pasted%20image%2020261120232504.png)
Он доступен, и он как раз и является нашим `route` в формате `ipv4` так как его `MAC-адрес` идентичен строке с пометкой `router`.

Нам остаётся теперь через `netplan` конфиг, поменять наш `route` на `192.168.11.254` и попробовать снова обратиться на `busybox.net`
```shell
sudo vim /etc/netplan # Меняем строку с 192.168.11.1 на 192.168.1.254
sudo cat /etc/netplan/*.yaml
```
![](../attachments/Pasted%20image%2020261120232758.png)

Теперь нужно применить наши изменения:
```shell
sudo netplan apply
ip route
```
![](../attachments/Pasted%20image%2020261120232849.png)
`default gateway` успешно поменялся, теперь проверим.

```shell
sudo wget https://busybox.net/downloads/busybox-1.38.0.tar.bz2
ls -la | grep "bus."
```
![](../attachments/Pasted%20image%2020261120233129.png)

Поздравляю, мы решили первую твою проблему с сетью, на живом примере. Такие кейсы конечно редкие, но они дают понимание что происходит при неправильном указанном `default route` в `Linux`.
