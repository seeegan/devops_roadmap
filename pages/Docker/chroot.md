Самым древним способом изоляции в Linux является `chroot`.

Давайте его рассмотрим и попрактикуемся сполна, поймём что это вообще такое.

## Шаг 1: Что такое `chroot` и зачем он нужен

`chroot` (расшифровывается как change root - изменить корень) - это системный вызов и утилита, которая меняет видимое для процесса (и его потомков) корневое дерево директорий (root directory).

Как это работает на пальцах:
Обычно у любого процесса есть корень `/`. Он видит `/bin`,`/etc`,`/home` и т.д. Когда ты делаешь `chroot` в какую-то директорию (например, `/home/new_root`), для этого процесса директория `/home/new_root` становится корнем `/`.

Давайте попробуем создать нашу новую директорию и поменять корень.
```shell
sudo mkdir /home/new_root
sudo chroot /home/new_root
```
![](../attachments/Pasted%20image%2020261119203321.png)
Мы получили ошибку что он не смог найти `/bin/bash`, догадываешься почему?
> Наш корень теперь /home/new_root в котором нет `bash`, то есть в нашем новом корне нет такого пути `/home/new_root/bin/bash`, а при `chroot ` он пытается запустить bash, и не находит этот бинарник.

Помимо того что `chroot` это программа, она также является и системным вызовом, то есть через `strace` мы можем нашу команду трассировать и посмотреть системный вызов `chroot`
```shell
sudo strace -e trace=chroot chroot /home/new_root
```
![](../attachments/Pasted%20image%2020261119203639.png)

Хорошо, раз у нас нет `bash` в нашей новой корневой директории, давайте его скопируем, как мы уже ранее выясняли "В Linux всё есть файл", чтобы найти где лежит нужная нам программа, можно использовать программу `which`
```shell
which shell
```
![](../attachments/Pasted%20image%2020261119204013.png)

Но нам недостаточно будет просто скопировать этот бинарник, ведь у любой программы есть зависимости, и чтобы всё корректно работало нам нужно будет их перенести.

Чтобы убедится что это не будет работать, давайте сделаем неправильно:
```shell
which bash
sudo mkdir -p /home/new_root/usr/bin/
sudo cp /usr/bin/bash /home/new_root/usr/bin/
ls -la /home/new_root/bin
```
![](../attachments/Pasted%20image%2020261119205312.png)

Есть ещё удобная утилита `tree` показывает дерево указанного каталога:
```shell
tree /home/new_root/
```
![](../attachments/Pasted%20image%2020261119210645.png)

И так, `bash` у нас есть, пробуем снова сменить root.
```shell
sudo chroot /home/new_root
```
![](../attachments/Pasted%20image%2020261119210709.png)
Хммм, не получилось, может быть попробовать указать ему напрямую где находится bash в нашем новом корне

```shell
sudo chroot /home/new_root /home/new_root/usr/bin/bash
```
![](../attachments/Pasted%20image%2020261119210816.png)

Кажется что должна быть ошибка зависимостей, да? Но почему он нам просто сообщают что такого файла не найдено.

Дело в том, что `chroot` или даже `dmesg`  не скажут нам напрямую что не хватает библиотеки `X`, для этого нужно смотреть в ядро. Давай попробуем ту же команду только "под микроскопом"

```shell
sudo strace -e trace=openat,open chroot /home/new_root /home/new_root/usr/bin/bash
```
![](../attachments/Pasted%20image%2020261119211230.png)

Как видно по трейсу, ядро пытается открыть файлы зависимостей, библиотеки, но наш новый `root` это `/home/new_root`, в нём нет даже каталога `/usr/lib`, поэтому наш `root` сменить не получается, он не может запустить `bash`.

Конечно круто смотреть через `strace` какие зависимости пытается открыть ядро, но это слишком уж неудобно, для этого есть программа `ldd`.

`ldd` - (List Dynamic Dependencies - список динамических зависимостей) - это утилита, которая показывает, какие разделяемые библиотеки (shared libraries) требуются программе для запуска.

Возвращаясь к нашей практике, теперь мы понимаем что bash не запустится в новом корне без зависимостей, поэтому нам нужно их перенести.

Смотрим список зависимостей для `bash`:
```shell
ldd /usr/bin/bash
```
![](../attachments/Pasted%20image%2020261119211847.png)

Нам нужны зависимости у которых есть реальный путь. Как мы видим `libtinfo.so.6 => /lib/x86_64-linux-gnu/libtinfo.so.6 (0x00007f198d40d000)` `libtinfo.so.6` - это символьная ссылка на зависимость котоая лежит по пути `lib/x86_64-linux-gnu/libtinfo.so.`, а значит нам нужен именно этот путь. `(0x00007f198d40d000)` - это нам не нужно, это адрес в памяти.

`linux-vdso.so.1` - Нам не нужно, `ldd` честно выводит всё, что видит в таблице зависимостей бинарника. Но поскольку `vDSO` — это виртуальная штука, которую ядро подсовывает само, **копировать её в твой `new_root` не нужно**. Тебе нужны только те зависимости, у которых указан реальный путь (например, `libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6`)

И такс, разобрались с зависимостями, нам нужно будет только 3 строки:
- `/lib/x86_64-linux-gnu/libtinfo.so.6`
- `/lib/x86_64-linux-gnu/libc.so.6`
- `/lib64/ld-linux-x86-64.so.2`
Эти 3 зависимости мы поместим в наш новый корень в каталог `/usr`

```shell
sudo cp --parent /lib/x86_64-linux-gnu/libtinfo.so.6 /lib/x86_64-linux-gnu/libc.so.6 /lib64/ld-linux-x86-64.so.2 /home/new_root/usr/
```
`--parent` - для того, чтобы он автоматически создал `/lib` при копировании

```shell
tree /home/new_root
```
![](../attachments/Pasted%20image%2020261119213625.png)

Наши зависимости успешно скопированы, теперь давайте попробуем запустить `chroot` с `bash`:
```shell
chroot /home/new_root bash
```

> Тут я немного ошибся в путях, и ничего не работало, в общем нужно переносить не в `/usr`, а сразу в корень, в этом была моя ошибка.

![](../attachments/Pasted%20image%2020261119215137.png)
Должно быть так, то есть не в `/home/new_root/usr`, а сразу в корне `/home/new_root`.


```shell
chroot /home/new_root bash
```
![](../attachments/Pasted%20image%2020261119215248.png)

Всё, мы переключились на новый корень, в bash, правда большинства команд тут нет, поэтому мы можем установить buxybox, это стандартный набор утилит необходимый для работы в терминале.

```shell
sudo wget https://busybox.net/downloads/binaries/1.35.0-x86_64-linux-musl/busybox
ls -la /home
```

Теперь нам нужно дать ему права на выполнение, ведь это executable файл:
```shell
file busybox
```
![](../attachments/Pasted%20image%2020261120235324.png)

```shell
sudo chmod g+x,o+x busybox
```
`g` - `group` (группа), указываем какие права назначаем для группы
`+x` - добавить права на выполнение `execute`
`o` - `other` (остальные), указываем какие права назначаем для тех, кто не попадает в группу владельца файла
```shell
ls -la busybox
```
![](../attachments/Pasted%20image%2020261120235646.png)

Теперь перемещаем его в наш новый корень:
```shell
sudo mv busybox /home/new_root/bin/
tree /home/new_root/
```
![](../attachments/Pasted%20image%2020261120235820.png)

Снова меняем корень
```shell
sudo chroot /home/new_root bash
```

```shell
ls
bash: ls: command not found
bash-5.2  /bin/busybox ls
```
У нас не настроены относительные пути, поэтому для использования  busybox приходится прописывать полный путь.

Давайте установим все символьные ссылки:
```shell
/bin/busybox --intstall -s
```


### Разворот
Я хотел использовать `bash` для демонстрации, но с этим возникает большая проблема. Сам `bash` мы запустить без проблем можем, да, но вот в `busybox` - `bash` отсутствует, что нам говорит о том, что мы не сможешь запустить и `bash` и `busybox` одновременно. Когда мы устанавливали `busybox` подразумевалось что мы запустим именно его и в качестве аргумента передадим `sh` который уже есть. В целом ничего не отличается. Просто наша команда будет выглядеть так:
```shell
sudo chroot /home/new_root busybox sh
```

В общем процесс изменился, а переписывать всё лень, вместо bash, я поставил `sh`, и зависимости взял именно из него, поместил я его в `/home/usr/bin/sh`. Это единственное что отличается. 

И так, у нас есть новый корень, с работающими командами и новой оболочкой, давайте попробуем посмотреть на процессы в нём, какие процессы видит данный корень и изолирован ли он вообще.

```shell
ps
```
![](../attachments/Pasted%20image%2020261121005132.png)

Мы видим ошибку, он вполне логична, у нас нет псевдо-файловой системы `/proc`, она создаётся ядром при запуске системы и постоянно туда добавляет новые интерфейсы для взаимодействия. 

Нам нужно создать эту ФС `/proc`, записать на неё ФС и смонтировать в эту точку.

Создаём директорию:
```shell
mkdir /proc
```

А теперь нужно записать на неё ФС и смонтировать:
```shell
mount -t proc none /proc
```
- С `mount` мы уже знакомы
- `-t` - флаг для указания типа файловой системы, в нашем случае это псевдо-файловая система, поэтому этап с записью файловой системы на "диск" мы пропустили
- `none` - у `/proc` нет физического носителя, это виртуальная файловая система созданная ядром
- `/proc` - наш каталог куда монитируем файловую систему

В общем случае синтаксис команды `mount` выглядит следующим образом
```
mount [опции_команды] [-t тип_ФС] [-o опции_монтирования] файл_устройства точка_монтирования
```

```shell
ps
```
![](../attachments/Pasted%20image%2020261121010714.png)
Как мы видим процессы хостовой машины от нашего корня никак не изолированны, поэтому он видит все процессы.

Метод `chroot` разобран полностью, он не подходит для корректной изоляции, для "трушной" изоляции мы будем испоьзовать `namespaces`.
